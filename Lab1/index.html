Your Linux environment

image vs. container, the shared folder, what runs where
Lecture

One folder, two names

10 min

Your CSS 342 programs are compiled and graded with g++ on Linux, and a program that builds and runs on your laptop's compiler can fail or behave differently there. A container gives everyone the same Linux, the same compiler, and the same tools (make, gdb, valgrind) on any computer. The one thing to get straight is where each file lives: on your computer, inside the container, or both.

  • Image vs. container. The image cssimages/linuxlab is a read-only template, like an installer disk. Your container cssskl342 is a running Linux machine made from it, once, by docker run. You can delete a container and make a new one from the same image.
  • One folder, two names. /home/cssuwbstudent/CSSSKL342 in Linux is C:\Users\you\CSSSKL342 on Windows (/Users/you/CSSSKL342 on a Mac). hello.cpp is one file; a change made on either side is the same change. Everything else in Linux, like notes.txt in the picture, lives only in the container.
  • What runs where. The VS Code window is on your computer, but it is attached to a VS Code Server inside Linux: the files it opens, its terminal, and g++ are all in the container. Check the bottom-left label: Container … (cssskl342).
  • Linux rules apply inside. A program compiled by Linux's g++ runs only in Linux. rm deletes for good: there is no Recycle Bin or Trash. And Linux file names are case-sensitive (Stack.h and stack.h are different files), while Windows and macOS file names usually are not.

TermExampleWhat it means
File namesum.cppThe name alone, no folders. The part after the last dot, .cpp, is the extension; it tells people and tools what kind of file it is. Linux programs usually have no extension (sum).
Folder (directory)made-on-my-computerA container for files and other folders. "Folder" and "directory" mean the same thing.
Full path (absolute path)/home/cssuwbstudent/CSSSKL342/part0/made-on-my-computer/sum.cppEvery folder from the very top down to the file. Current folder (working directory)/home/cssuwbstudent/CSSSKL342/part0Where your terminal is right now: the prompt shows its last part, pwd prints all of it, and cd changes it.
Relative pathmade-on-my-computer/sum.cppA path that starts from the current folder, so it does not start with /. The same file has different relative paths from different places: from inside made-on-my-computer, it is just sum.cpp.

Special names you can use in any path:

  • ~ is your home folder, /home/cssuwbstudent; so ~/CSSSKL342 is a full path in short form.
  • . is the current folder; ./sum means "the program sum in this folder". Linux only runs programs from the current folder if you say so, which is why you type ./hello, not hello.
  • .. is the folder one level up: from made-on-my-computer, cd .. takes you back to part0.

Things that trip people up:

  • Separators: Linux uses /; Windows uses \. Inside the container (VS Code's terminal, your code, your Makefiles), always use /.
  • Capital letters: in Linux, Sum.cpp and sum.cpp are different names (see "Done early?" challenge 1).
  • Spaces: ls my notes.txt looks for two files, my and notes.txt. Put quotes around a name with spaces (ls "my notes.txt"), or better, don't use spaces in file names for code.
  • Relative paths depend on where you are. g++ sum.cpp only works if the current folder contains sum.cpp. If you get No such file or directory, run pwd and ls first. The same idea applies to #include "convert.h" in Part 1: the compiler looks for it relative to the folder of the file that includes it.

How C++ programs are built

headers, compiler vs. linker, make, cppcheck
Lecture

The build model

15 min

In Java, javac finds your other classes for you. In C++, you tell the compiler which files to compile and the linker which pieces to join, and every multi-file CSS 342 assignment depends on getting this right. Most confusing build errors (undefined reference, multiple definition, redefinition) make sense once you know which stage is complaining.

  • Three stages. The preprocessor pastes #included files in as text. The compiler turns each .cpp (with its includes) into an object file .o, one at a time, without seeing the others. The linker joins the .o files and matches every function call to exactly one definition.
  • Declaration vs. definition. A header (.h) holds declarations: "this function exists, with this signature." The .cpp holds the one definition (the body). The compiler only needs the declaration; the linker needs the definition.
  • Include guards stop a header from being pasted twice into the same .cpp: 
    #ifndef CONVERT_H
#define CONVERT_H
// ... declarations ...
#endif
    The first time a .cpp includes the file, CONVERT_H is not yet defined, so the contents are kept and CONVERT_H gets defined; the second time, the whole file is skipped. Each header needs its own macro name. #pragma once as a header's first line does the same job (Exercise 1's report.h uses it; its comments explain it).
  • #include <iostream> vs. #include "convert.h": angle brackets for the standard library, quotes for your own headers (searched in the including file's folder first). The comments at the top of Exercise 1's main.cpp say more.
  • Global (free) functions. In C++ a function does not have to belong to a class. celsiusToFahrenheit in Exercise 1 is declared in convert.h, defined in convert.cpp, and called by name, celsiusToFahrenheit(100.0), from any file that includes the header: no object, no class name. main is a global function too. (Java's nearest equivalent is a static method such as Math.sqrt.)
  • Namespaces. The standard library is in the namespace std: the full name of cout is std::cout. A .cpp file can write using namespace std; after its includes and then just cout; never put it in a header, where it would apply to every file that includes the header. From here on, every .cpp in these labs uses using namespace std; and the short names; headers keep std::.
  • Compiler errors vs. linker errors. Compiler errors have a file and line number. Linker errors say undefined reference or multiple definition, have no line number, and end with ld returned 1 exit status. Knowing which one you have tells you where to look.
  • Commands: 
    g++ -std=c++17 -Wall -Wextra -g -c convert.cpp             # compile only: makes convert.o
g++ -std=c++17 -Wall -Wextra -g -o app main.o convert.o   # link
make                            # rebuild only what changed, using the Makefile
cppcheck --enable=all *.cpp     # static analysis: finds bugs the compiler misses
    Always compile with -Wall -Wextra and treat warnings as bugs.
Coming from JavaJava has no separate linker step and no headers: javac reads the other classes directly. In C++ each .cpp is compiled alone and only knows what its headers tell it. A C++ namespace is like a Java package, and using namespace std; is like import java.util.*;.

    (from convert.o; addresses may differ).     Show what happens

    (a) Compiler: report.cpp:7:35: error: 'celsiusToFahrenheit' was not declared in this scope. (b) Linker: undefined reference to `celsiusToFahrenheit(double)' and `fahrenheitToCelsius(double)', then ld returned 1 exit status: both Us from the previous challenge are left unmatched.

    Show what happens 
    g++ -std=c++17 -Wall -Wextra -g -c main.cpp
g++ -std=c++17 -Wall -Wextra -g -c convert.cpp
g++ -std=c++17 -Wall -Wextra -g -c report.cpp
g++ -std=c++17 -Wall -Wextra -g -o temps main.o convert.o report.o

    All three .o rules list convert.h, so a change to that one header recompiles everything. Run make to actually build.

    CXX      = g++
CXXFLAGS = -std=c++17 -Wall -Wextra -g

temps: main.o convert.o report.o
	$(CXX) $(CXXFLAGS) -o $@ $^

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $<

main.o: convert.h report.h
convert.o: convert.h
report.o: report.h convert.h

clean:
	rm -f *.o temps
    Show what happens

    %.o: %.cpp means "any .o is built from the .cpp with the same name"; $@ is the target, $^ all its dependencies, $< the first one. The three short lines add each file's headers. The first build runs the same four commands as before; after touch report.h it recompiles only main.cpp and report.cpp (the two rules that list report.h), then relinks.

Walkthrough 1

10 min

We build the original code live, read each error message together, and classify it. Topics: why a function body in a header breaks the link, why guards work per .cpp file only, and how make uses file timestamps.

Organization vs. correctness. How code is organized and whether the program runs correctly are two separate things. 1.1.all_in_one_file/temps.cpp is Exercise 1's fixed program with everything in one file, with no headers and no Makefile, and its output is identical to the five-file version (its README.txt shows the comparison). The computer doesn't care; very differently organized code can produce exactly the same output. People do care. Well-organized code is easy to read and understand: each file has one job, and a header shows what a module offers without its details. It is also easy to keep changing: make rebuilds only what you touched, modules can be reused, and several people can work at once. A 50-line program hardly needs it; a CSS 342 assignment you keep extending for weeks does.

Self-test (after the walkthrough)
  1. You compile main.cpp alone with g++ -c main.cpp, and it succeeds, even though celsiusToFahrenheit() is not defined anywhere yet. Why is that not an error?
    Show answer

    Compiling one .cpp only needs declarations, and convert.h declares celsiusToFahrenheit. Nobody checks for the definition until the linker runs, and then you get undefined reference to celsiusToFahrenheit(double).

  2. You get main.cpp:20:9: error: 'printRow' was not declared in this scope. Compiler or linker? What is the likely cause?
    Show answer

    Compiler: it has a file and a line number. main.cpp calls printRow without having seen its declaration, so most likely #include "report.h" is missing (or the name is misspelled).

  4. A classmate puts int helper() { return 1; } in a guarded header that two .cpp files include. What happens, and what are two ways to fix it?
    Show answer

    A linker error, multiple definition of helper(): each .cpp gets its own copy, and guards only prevent duplicates within one .cpp. Fix: keep only the declaration in the header and move the body to one .cpp, or mark it inline.

Types, conversions, and limits

sizes, overflow, casts, floating point
Lecture

Numbers are not the same as in Java

10 min

A type tells the compiler how many bytes a value takes and which operations make sense on it, so mistakes like multiplying a string are caught before the program ever runs. C++ types sit close to the hardware: their sizes can differ between machines, and an int that overflows silently wraps around instead of throwing. Real programs also mix types all the time (an average is a double computed from int totals; an index is compared with a size), so you need to know when C++ converts for you, when a conversion loses information, and how to convert on purpose with a cast.

  • Sizes are not fixed. int is usually 32 bits, but long is 64 bits with g++ on Linux and 32 bits with Visual C++ on Windows. Ask the compiler with numeric_limits (<limits>).
  • Unsigned types exist and wrap around; sizeof and .size() return them. Mixing signed and unsigned in comparisons is a common bug, and -Wall warns about it. Signed overflow, on the other hand, is undefined behavior: the program may do anything, not just wrap. (Reading for later: 2.1.signed_unsigned_bug/signs.cpp and its README.txt show two signed/unsigned bugs and their fixes.)
  • Arithmetic happens in the operands' type, before the result is stored: 
    int big = 2000000000;
long long p = big * 2;    // overflows in int first, THEN converts
double h = 7 / 2;         // 3.0, not 3.5: integer division happened first
  • Conversions. Prefer static_cast<double>(x) to C-style (double)x: it is easier to search for and refuses unsafe conversions. Casting a double to int truncates toward zero.
  • Floating point is approximate. Never compare doubles with ==.
Coming from JavaJava fixes every type's size and defines integer overflow to wrap. C++ does neither, and has unsigned types that Java lacks.

References and parameter passing

value, &, const &, returning references
Lecture

Value, reference, const reference

15 min

Every function call has to settle one question: does the function work on the caller's variable, or on a copy of it? Java decides for you (primitives are copied, objects are shared); C++ lets you choose for every parameter of every type. The choice affects correctness (can the function change my variable?) and speed (copying a large object on every call is costly), and const & gives you the speed without the risk.

  • Reference variables: int &r = i; makes r another name for i; no new int is created, so changing r changes i. A reference must be initialized when it is declared (int &r; doesn't compile), and it can never be made to refer to a different variable afterwards. Compare int x = i;, which creates a separate int holding a copy of the value.
  • Pass by value (void f(int n)): the function gets a copy. This is the default for every type, including objects.
  • The Java habit. Coming from Java, it is natural to write 
    void addItem(string list, string item) {
    list += item;        // changes the COPY only
}
    and expect the caller's list to change. It doesn't: list is a full, separate copy, and it disappears when the function returns. No error, no warning; the caller's string is simply unchanged. In your CSS 342 assignments this is the bug "my insert doesn't change my list". The fix is one character: string &list.
  • Pass by reference (void f(int &n)): n is another name for the caller's variable. Use it when the function must change the argument, or to return more than one result.
  • Pass by const reference (void f(const string &s)): no copy, and no changes allowed. The default way to pass objects in your CSS 342 assignments.
  • Rule of thumb: built-ins (int, double, char) by value; objects by const&; plain & only to change the argument.
  • Returning a reference lets a call appear on the left of =: the call is the variable it returns, so assigning to the call assigns to that variable. This is how operator[] works on containers. For example: 
    // Returns a reference to the counter that score belongs in.
int &counterFor(int score, int &passCount, int &failCount) {
    if (score >= 60) {
        return passCount;
    }
    return failCount;
}

int passCount = 0, failCount = 0;
counterFor(85, passCount, failCount) = 7;   // the call IS passCount: passCount = 7
counterFor(40, passCount, failCount)++;     // the call IS failCount: failCount++
// now passCount is 7 and failCount is 1
    If counterFor returned int instead of int&, the call would be just a temporary copy of the value, and both lines fail to compile: lvalue required as left operand of assignment. Never return a reference to a local variable: it is destroyed when the function returns.
  • & in a declaration means "reference." In an expression, &x means "address of x" (pointers come in a later lab).
Coming from JavaIn Java, objects are reached through references, so a method can change the object you pass. In C++ an object parameter is a full, independent copy unless you write &.
